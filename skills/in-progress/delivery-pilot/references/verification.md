# Verification ownership

Assign evidence gathering separately from acceptance. The existing boundary's
criteria and repository rules determine who may satisfy a gate.

## Classify each check

Split mixed checklist items into observable steps and the decision they inform.
Record each step's expected result, environment, execution owner and acceptance
owner in the existing verification plan.

| Kind | Agent work | Remaining human work |
| --- | --- | --- |
| Mechanical | Luna runs exact commands, tests, schema/JSON, stream, bounds, navigation and redaction checks; Sol assesses questionable evidence | None when the accepted contract permits agent proof and the required environment was exercised |
| Observable interaction | Luna drives the available terminal/browser and captures the real candidate; Sol inspects layout, errors and interaction against the agreed rubric | Native checks in inaccessible environments and subjective judgments the rubric does not settle |
| Acceptance or authority | Agents prepare evidence, a concrete recommendation and the smallest executable remaining checklist | Product judgment, explicit human-only checks, permission decisions and candidate approval |

Start with the existing implementer and reviewers. A separate Luna execution
worker is useful for a substantial mechanical checklist with independent access;
a fresh Sol verifier is useful when interpreting the evidence needs judgment.
Name the actual tool/environment capability before dispatch. Neither model has
access to a native device or independent desktop merely because it can reason
about it.

## Evidence boundaries

- Run against the exact candidate and required environment. Record what ran,
  expected versus observed outcome, output mode and retained evidence.
- Separate controlled-fixture results from native observations and authorized
  mutation/readback proof; retain their different limits in the handoff.
- Select production captures for changed states and distinct layout risks,
  preserving repository-required examples. Expand widths or modes when they test
  another risk. Record candidate, scenario, expected/observed exit, width and mode
  beside captures. Inspect actual output: JSON/exit assertions, rendered images,
  terminal captures and native interaction establish different things.
- Link exact result files from the current handback and derive permanent-test
  totals from them. Label scratch capture execution separately. Keep historical
  results revision-labelled so earlier counts cannot appear current.
- Execute generated next commands through the parser. Preserve scope and
  selection; a plausible-looking command is not navigation proof.
- Extend live checks to mutations only within concrete existing authority and
  isolation. Reconcile uncertain effects before any retry.
- Refresh only evidence affected by a changed candidate, dependency or
  environment; keep the original tested revision for carried-forward results.

## Preserve acceptance ownership

An agent can perform the commands inside a human checklist and leave useful
results even when the human still owns its decision. Describe these as
agent-executed evidence. Keep an explicitly human-owned checkbox open until the
named human supplies acceptance or explicitly changes the contract's owner.
Existing independently launched native-terminal requirements remain binding.

When a requirement genuinely needs only observable output, propose assigning its
execution to an agent during preparation. Where the approved boundary already
allows agent evidence, run it without inventing a new approval gate. Where the
approved boundary explicitly requires human execution, ask for that specific
ownership change before marking the requirement satisfied; continue independent
checks while awaiting the decision.

The final checklist gives the human only residual steps, their exact candidate
and prerequisites, copyable commands where useful, and the expected observations.
Retain earlier evidence and human annotations. An agent's recommendation is not a
human vote or product acceptance.
